# Diagram Direction

Use this reference when a page depends on a process, architecture, relationship, structure, or scientific plot. It routes the visual carrier and refinement path; it does not create another Agent, PRD, or approval step.

The page-group planner defines the diagram's communication job and page-level visual solution inside the shared Deck direction. The visual director owns the final composition. A layout engine may propose geometry, but it cannot approve the result.

Before selecting a renderer, classify the carrier as **quantitative**, **conceptual**, or **mixed**. Quantitative geometry comes from declared data and keeps visible fields, units, domains, baselines, labels, uncertainty, transformations, and source. Conceptual geometry comes from named entities and relationships. Mixed carriers visibly separate those two meanings. Never choose a stock mark because a title merely sounds like a curve, bar, point field, or layer.

## Route by diagram type

- **Conceptual diagrams — default: image-first hybrid assembly.** Generate or acquire suitable visual assets first, inspect them, then combine them with editable labels and connectors using the hybrid object workflow below. This applies to ordinary processes, abstract systems and architecture as well as physical objects; texture is not a prerequisite. A meaningful source image or illustration should carry recognition and explanation, not become a decorative icon on a generic box. This material choice does not replace source figures or real-data plotting.
- **Simple relationships better expressed with native geometry:** Mermaid is an optional choice for simple relationships, not the default. Use it when concise nodes and native relationships are clearer than image assets, or when explicitly requested. Read `mermaid-presentation.md` during page design. Simple vector objects or a self-contained SlideBlocks SVG are also valid when they communicate more directly; keep page prose in measurable HTML and only concise intrinsic labels inside SVG.
- **Repeated explanatory comparison or one annotated irregular conceptual visual:** follow `figure-spec.md`. Use the `comparison` recipe to give every peer one shared `title / visual / note` anatomy, or the `annotated` recipe to allocate HTML callouts around named anchors. The recipe controls slots, gaps, rails, and containment only; a subject-specific renderer controls the marks. Keep that custom drawing inside the assigned visual slot instead of hand-positioning the complete figure.
- **Custom architecture or relationship graph requiring explicit ports or drawing control:** follow `diagram-spec.md` when its supported graph renderer fits the material. First express a semantic graph with the required nodes, groups, ranks, edges, exact endpoint or port meanings, and edge-owned labels. Load the real fonts and measure the actual labels. Let ELK calculate initial node positions and connector routes, then let SlideBlocks refine hierarchy, scale, spacing, anchors, labels, and paths before rendering the final SVG. Complexity alone does not select this route; first reconsider how much belongs in the drawing and how much room it needs.
- **Mermaid-to-Excalidraw:** use only as an optional editable draft route for a simple graph that Mermaid already describes well. The conversion is not a composition decision, does not replace SlideBlocks refinement, and is not the default route for a dense architecture diagram.
- **Quantitative chart, scientific plot, heatmap, or other data graphic:** use a source figure or render it from the real dataset with an appropriate plotting tool. Keep fields, labels, values, units, domains, baselines, uncertainty, transformations, legends, and source context visible and measurable. The current FigureSpec visual layer is not a ChartSpec and must not use unlabeled bars or curves as a substitute. Avoid enlarging raster output beyond a sharp projection result.

`Custom` describes an expression choice, not a rendering route. For every selected code-backed diagram or chart, record one executable `renderRoute` in `execution-lock.json` and repeat the exact value plus its stable `A<NN>` ID on the mounted carrier with `data-slideblocks-render-route` and `data-slideblocks-asset-id`. Use `diagram:mermaid`, `figure:comparison`, `figure:annotated`, `figure:graph`, `diagram:elk`, or `direct-svg`; generated routes also record the project-local generator. The project validator must reject a missing, unknown, or source/lock-mismatched route before browser QA.

`direct-svg` is the narrow escape hatch, not the default custom route. Use it only when the complete relationship is self-contained in one semantic SVG and its concise intrinsic labels share that coordinate system. Mark the final SVG with `data-layout-engine="direct-svg"`, `data-layout-role="final"`, `data-visual-renderer="slideblocks-svg"`, stable node/edge ownership, and the matching render route. If visible HTML must sit over an SVG curve, axis, region, node, or boundary, use FigureSpec instead; an absolutely positioned sibling label has no measurable ownership merely because it looks aligned once. Page titles and prose may remain outside the carrier in normal page regions.

## Hybrid object workflow

Plan the objects and their relationships together with the page. Keep the factual or conceptual relationship model authoritative; generated appearance is illustrative, not observational or quantitative evidence.

When the composite must satisfy a primary explanation slot, register the final diagram with its traceable relationship model as `diagram / source-derived`; keep generated constituent imagery separately identified in the source map. Adding connectors does not turn generated appearance into proof of a real object or measured result. Review the composite's actual explanatory meaning under the existing evidence gates.

1. In the existing Page Brief, identify the visual assets that make each entity or stage recognizable and which names, relationships and formulas must remain editable. Prefer relevant original material for factual objects; use generated illustrations for conceptual appearance. Describe palette, viewpoint, relative visual weight, approximate aspect ratio, empty space and intended connector landing regions. Generate or acquire needed assets before the final composition lock; inspect their actual shapes and adjust the proposed layout. A complete generated diagram draft is optional, not the final page or a prerequisite for generating individual assets.
2. Use the current Agent's available image-generation tool or its installed image-generation skill. Let that capability select its supported model; do not hard-code a provider or version in this Skill, install another provider, or claim an unverified model version. If unavailable, use a suitable existing asset or a simpler vector treatment and record the limitation. Generate object assets without text, formulas, arrows or relationship labels by default. Choose separate objects or a shared strip according to the page's positioning and editing needs; no fixed object count or equal-column layout is required.
3. Inspect the generated result before assembly: consistent style, recognizable objects, complete silhouettes, usable resolution and space for labels. Verify real alpha rather than accepting a painted checkerboard. A plain background matching the page is also valid; verify any compositing in print and offline output. Save the assets and prompts locally and record generated provenance in the existing source map. Use the image-generation capability for pixel corrections; do not trace away useful texture merely to obtain an SVG file.
4. For a simple self-contained relationship, the supported assembly is a hybrid SVG: embed local object bitmaps, keep concise intrinsic labels and connectors as editable SVG, and retain the existing `direct-svg` semantic ownership and final-geometry contract. This is hybrid, not pure vector. Derive object anchors from the visible subject after scale/crop, not just the rectangular image bounds; preserve named entities and exact edge endpoints. Page headings, prose and formulas stay in normal HTML/KaTeX regions. More involved layouts retain their existing FigureSpec/DiagramSpec routing and must verify that their selected renderer supports the image carrier; a handwritten overlay is not a substitute for that contract.
5. Let the page's type scale control label sizes. Shape connectors for the actual relationship: where a smooth return is appropriate, use continuous curvature and deliberate endpoint tangents rather than a long rigid middle with tight bends. Keep labels independently editable, usually horizontal, with measured clearance from every painted curve, marker and object. Judge the complete page in live, reduced-motion, copied-offline and print states; image quality or editable geometry alone does not approve the result.

## Route implementation dependencies by visual grammar

- Curves and parameterized paths inside a subject-specific renderer may use `d3-shape`; legitimate data or model mappings may use `d3-scale`. Neither dependency supplies semantic fields, labels, units, or provenance by itself.
- Native Mermaid loads only the selected type's required packages and optional local icon collection. Custom DiagramSpec graphs use `elkjs` for candidate geometry.
- For an explicitly experimental presentation-sized graph, `diagram-spec.md` documents the bounded fit adapter and local icon lookup. Its current rectangular-node subset does not implement every semantic feature mentioned in the route above; do not silently drop groups, lanes, ranks or shapes. A first-fit result remains a candidate for full-slide review.
- Spatial, physical, biological, and other concept visuals use suitable native SVG marks, the hybrid object workflow, or a supported bounded FigureSpec visual renderer with named anchors.
- Formulas reuse the presentation project's KaTeX rather than introducing a second formula stack.
- TikZ is only a reserved future visual-leaf adapter boundary; this release does not ship the adapter. A later implementation would still require TeX-native source or math geometry and an already pinned toolchain. It is not the fallback for ordinary untidy layouts, and Skill activation never installs TeX.

Load only the dependencies used by the selected page. Do not install complete `d3`, an interactive canvas editor, or domain-specific packages merely because the page contains a diagram.

## Approve the rendered page, not the tool output

- Treat ELK, Mermaid, Excalidraw, and plotting output as production material rather than aesthetic approval.
- Treat FigureSpec's resolved SceneIR the same way. The recipe may prove equal peer slots, callout capacity, named-anchor landing, and visual-slot containment; it cannot approve page-scale hierarchy or taste.
- Run the last geometry gate against the actual SVG embedded in the rendered live slide and copied `offline.html`, after fonts load. Native Mermaid follows `mermaid-presentation.md`; SlideBlocks-authored semantic SVG keeps `data-slideblocks-diagram="final"` and its existing ownership/geometry gate after every refinement. A passing candidate, geometry JSON, or unused generated SVG is not final approval.
- For SlideBlocks-authored SVG, measure painted geometry instead of visual masking. An opaque label backing placed over a continuous connector does not create clearance; move the label, reroute the connector, or split the painted path around the label. Native Mermaid may use its normal on-edge labels with a backing; verify their ownership and visibility without claiming the custom SVG clearance gate passed.
- Inspect the diagram at its final size on the complete slide. Recompose or reroute it when the candidate geometry leaves weak hierarchy, awkward empty space, ambiguous endpoints, crossings, or labels that are too small at presentation distance.
- Make the diagram serve the page canvas and visual direction. Do not center a shrunken tool export inside an otherwise unused slide.
