# Task Routing

Choose content guidance from the audience's primary job, then choose visual expression independently. Infer both from the request, materials, existing deck, and viewing context; do not make the user select a task or style from a menu.

This is content routing inside the existing production workflow. It does not replace new-deck / existing-Slidev / migration / resume routing, the source-fidelity boundary, or the shared research, design, rendering, workbench, and offline-delivery contracts.

## Choose the audience job

| Audience needs to… | Load | Useful distinctions |
| --- | --- | --- |
| Understand a research finding, technical mechanism, or technical domain; judge what its evidence supports | [Research and technical communication](research-and-technical-communication.md) | Select the relevant existing depth guide inside that family. |
| Understand where work stands against a goal, what changed, what is blocked, and what should happen next | [Work progress report](work-progress-report.md) | Covers project updates, weekly/monthly reports, phase reviews, and team retrospectives. |

A subject word is not a route. A machine-learning project can need either family. A chart, citation, code sample, or the word “research” does not decide it. “汇报” / “report” alone is also insufficient: a paper-results report can still need the research family. Financial data alone does not turn a deck into a progress report or an empirical evaluation.

A programming lesson whose audience must read code, predict its behavior, explain a rule, or apply it in a small exercise belongs to Research and Technical Communication. That family selects its learner-oriented instruction guide; introductory learners do not have to qualify for an expert deep dive. A project update containing code still follows the progress job.

When both jobs are real, select the family that owns the main audience outcome and apply the other only to a bounded section or page. An engineering status deck may include one mechanism page; it does not need a complete technical lecture. A thesis defense may foreground contribution and evidence, while a mid-project checkpoint may foreground milestones and unresolved work. Do not load every guide for a mixed source bundle.

When neither family fits, infer a custom task from the actual audience outcome and continue through the shared workflow. Product launches, sales pitches, full courses, and exhaustive financial reporting are not newly specialized task modules. Preserve existing capabilities without claiming specialized coverage or forcing them into these two families.

For an isolated repair, style-only edit, or source-faithful migration, keep the accepted narrative and page boundaries. Task inference may clarify a page's role; it does not authorize a rewrite. On resume, reuse the recorded choice unless the user changes the audience outcome.

## Select visual expression separately

Use explicit style instructions and supplied templates, the accepted existing deck, applicable tastes, source material, and viewing conditions to select a direction from [style profiles](style-profiles.md) or synthesize a custom direction. A task family does not own a palette, font, background, density, or animation style.

- A research talk may use a classroom-like white canvas with code and progressive explanation, a figure-led scientific treatment, or a supplied corporate template.
- A work report may use a restrained briefing treatment, an established dark brand system, or the same academic treatment when it genuinely serves the audience.
- Academic / Scientific and Product Launch remain available directions, not task labels. Reference-informed directions are starting points, not verified Registry profiles.

Keep alignment, legibility, truthful evidence, editable source, reduced-motion/static states, and offline delivery common to every combination. Do not let a preferred visual style change the factual scope or content task.

## Record only what helps production

In the existing communication contract in `.slideblocks/page-plan.md`, briefly state the primary audience job, chosen family or custom task, why it fits, and any bounded secondary guidance. Keep visual direction in the existing visual-direction section. Do not add a task manifest, classifier service, required schema field, or second planning document.

Before implementation, check that the outline would change for a different audience job using the same materials. A progress report should expose state, variance, blockers, and next actions; a technical explanation should make the mechanism or evidence understandable. Merely changing titles and colors does not demonstrate routing.
